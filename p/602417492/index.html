CUDA Graph 的执行机制与动态性

本文最后更新于 2026年9月14日

关于 CUDA Graph，一个常见的第一印象是“不可变”：输入形状不可变、内存地址不可变、控制流不可变。但如果只记住这些限制，就很容易产生一些看似合理的推论。例如，LLM 的 decode 阶段上下文长度不断增长，因此无法使用 CUDA Graph。

实际情况恰好相反，decode 是推理框架使用 CUDA Graph 的典型场景。

本文先从一次 kernel launch 的提交过程出发，解释 CUDA Graph 保存了什么，再讨论其动态性，以及 PyTorch 如何管理 capture 期间产生的临时显存。

一次 kernel launch 提交了什么

CPU 启动 kernel 时，提交的是“执行这段 GPU 程序所需的工作描述”。理解这个过程，需要区分三类内容：

内容 例子 何时准备
kernel 代码 load、store、矩阵乘等机器指令 编译、加载时
一次执行的描述 程序入口、grid、block、参数、资源配置 launch 时
运行时数据 输入 tensor、权重、KV cache 执行前准备，执行中读取

下面以 NVIDIA GPU 上普通的 host launch 为例，分别讨论代码加载、参数准备和驱动提交。

代码加载与 kernel 启动

首先需要区分 kernel 的代码与某一次执行它的请求。

CUDA C++ 或 Triton 产生的 device 代码，最终需要转换为目标 GPU 能执行的机器指令。在 NVIDIA 平台上，PTX 是虚拟指令集，cubin 中包含面向具体架构的机器码，反汇编时通常称为 SASS。如果加载的是 PTX，驱动可以在加载过程中将其 JIT 编译为机器码；如果已经有适合当前架构的 cubin，则可以加载该二进制。

从提交到执行

驱动将函数、参数和执行配置组织为 GPU 可以处理的工作描述，再通知 GPU 执行。这里需要区分启动计算的命令与计算本身的指令：

内容 作用
kernel 机器指令 描述线程执行哪些 load、store、算术和控制流操作
提交命令与工作描述符 指定运行哪段代码、采用什么执行配置、使用哪些参数与依赖

host 指定 grid 和 block，具体的 block 分派和 warp 调度由 GPU 完成。因此，CPU 提交工作所需的时间，与 GPU 执行 kernel 的时间需要分别考察。

CUDA Graph 记录了什么

在普通的 eager 执行中，CPU 依次调用算子，经过框架的 dispatcher 和 CUDA runtime，将 kernel 提交到 GPU。对于计算时间很短的小算子，host 端的开销可能成为显著的性能瓶颈。

CUDA Graph 将一组 GPU 工作及其依赖关系预先定义为图，实例化后通过一次 graph launch 提交执行。stream capture 是构建这张图的一种方式，另外也可以通过显式的 Graph API 添加节点。CUDA 将这个过程划分为 definition、instantiation 和 execution 三个阶段，PyTorch 通常将最后一个阶段称为 replay。参见 CUDA Graphs 文档。

启动的线程数 8 8

第一次 replay 中，i = 5 的线程读到 0 后直接返回；第二次 replay 中，i = 5 的线程读到 6 并执行乘法。分支条件由 GPU 执行时读取的输入值决定，无须修改 graph。

调用方只使用有效数据对应的输出，padding 位置不会被此 kernel 更新。

为什么 decode 可以使用 CUDA Graph

首先需要明确 LLM 如何组织计算。用 T 表示本轮输入的总 token 数，H 表示 hidden size，hidden states 通常表示为 [T, H]：每一行对应一个 token 的隐藏向量。

常见 Transformer 中的 Linear、RMSNorm 和 MLP 都是 token level 的运算：对每个 token 的隐藏向量独立应用相同的变换。 例如，Linear 的矩阵乘 Y = X @ W 可以按行理解为：

这些 token 共享权重 W，但每一行的结果不依赖其他行。实现时通常将所有行合并为一次矩阵乘，以提高 GPU 利用率。RMSNorm 则沿每行的 hidden dimension 归一化，MLP 也分别变换每个 token 的向量。因此，对这些算子而言，T 个 token 来自一条请求还是多条请求，不影响逐 token 的计算方式。

attention 负责 token 之间的信息交互：每个当前 token 的 query，需要读取该请求中允许访问的 token 的 K/V。因此，attention 除了当前输入，还需要知道请求边界和历史 KV 长度。

在使用 KV cache 的普通单 token decode 中，每条请求每轮只输入一个新 token。Linear、RMSNorm、MLP 等算子只处理本轮的 T 个 token；attention 通过 KV cache 读取历史信息，无须重新计算历史 token 的这些逐 token 变换。只要本轮 token 数 T 固定，当前 hidden states 就保持为 [T, H]，即使历史 KV 长度仍在增长。

对于采用 paged KV cache 的实现，KV cache 可以来自预先分配的物理 block 池。逻辑序列访问哪些 block，由 block table 描述。跨越一个 block 边界时，框架可以分配新的逻辑映射，更新表项，而不移动整个 KV cache。

attention kernel 启动时，传入的是 sequence lengths buffer 的指针，而不是其中每条请求的长度值。capture 固定了这个指针；每轮 decode 只需更新 buffer 中的长度，例如从 [128, 256, 80, 512] 更新为 [129, 257, 81, 513]。kernel 在 GPU 上执行时，再从同一个地址读取本轮的长度，确定需要访问多少历史 KV。

sequence lengths 的内容改变，不需要更新 kernel 的启动参数。 在 kernel、grid、block 等其余启动配置也保持不变的前提下，不同 sequence length 就可以复用同一张 CUDA Graph。

block table 和 slot mapping 也可以采用相同的方式：保持 buffer 地址不变，通过更新表项指定读取哪些 KV block，以及将新 token 的 K/V 写入哪里。

prefill attention 的限制来自哪里

普通 decode 中，每条请求本轮只有一个 query token；prefill 中，每条请求本轮的 query token 数也会变化。即使总 token 数 T 相同，attention 的 launch grid 仍可能不同。

例如，两次 prefill 都有两条请求、总共 256 个 token，但请求长度分别是 [128, 128] 和 [192, 64]。Linear、RMSNorm、MLP 的输入都可以保持为 [256, H]；attention 则需要按请求处理各自的 query。

以 FlashAttention 2 的普通 forward 路径为例，host 按最长 query 长度计算分块数，再为每条请求、每个 head 启动对应数量的 block。假设选用的 kernel 每个 block 处理 128 个 query token，则有：

第一次 prefill 第二次 prefill
两条请求的 query 长度 [128, 128] [192, 64]
总 token 数 T 256 256
最长 query 长度 128 192
每条请求、每个 head 启动的 block 数 1 2

这里的分块数按 ceil(最长 query 长度 / 128) 计算；128 是本例选取的 query 分块大小。对应逻辑见 FlashAttention 的 grid 计算，最长 query 长度由 host API 传入。

如果按第一组输入 capture，图中为每条请求记录的只有一个 block。第二组输入中，第一条请求需要两个 block；直接 replay 原图，就缺少处理后 64 个 query token 的 block。更新 device buffer 中的请求长度和边界，不会改变已经捕获的 grid。

这就是仅按 T 复用 prefill graph 可能失败的具体原因。要让这两组输入复用同一张图，可以提前按足够大的 query 长度上限建图，让 kernel 从 device metadata 读取实际长度并跳过多余分块，同时保证其他启动参数和 buffer 地址也兼容。

如果 attention 路径仍需要 CPU 每轮重新计算 launch，框架可以采用 piecewise CUDA Graph：只捕获 attention 前后的计算，attention 每轮正常启动。

capture 期间的执行语义

“执行”在这里需要区分 host 与 device。

在 with torch.cuda.graph(g): 内，Python 代码仍然执行，算子的 host 端实现也会被调用。框架需要计算 metadata、选择 kernel、分配输出 tensor，并调用 CUDA API，这样才能知道应当向图中添加哪些节点。

但提交到正在 capture 的 stream 中的 GPU 工作不会在此时执行，而是被记录为 graph 节点。capture_end 得到图，后续 graph launch 才会执行其中的工作。这是 CUDA stream capture 的定义。

这里使用原地写入，是为了保留一个确定的输出初值。如果在 capture 内使用 static_y = static_x + 1，PyTorch 同样会创建输出 tensor，但在首次 replay 前，不应把它的内容当作这次加法的结果。

一些封装会在 capture 前运行 warmup，在 capture 后立即 replay，因此观察外层函数时，可能会看到输出已经完成计算。那是封装额外执行的结果，不能据此认为 stream capture 本身执行了被记录的 kernel。

为什么同步和读取结果会失败

capture 期间，GPU 工作尚未被提交执行，自然不能要求 CPU 等待其中某个结果完成。常见的不兼容操作包括：

  • 对正在 capture 的 stream 调用 cudaStreamSynchronize 或查询执行状态。
  • 对 captured event 调用 cudaEventSynchronize 或查询完成状态。
  • 调用覆盖当前 capture 的 device 级同步，例如 torch.cuda.synchronize()。
  • 通过 CUDA tensor 的 .item() 或需要同步的拷贝，将数据读回 CPU 并参与后续计算。

这些限制针对的是 capture 中的执行状态及其依赖，并不是所有与 stream 或 event 有关的 API 都被禁止。例如，符合 capture 规则的 cudaEventRecord 和 cudaStreamWaitEvent 可以用来建立图内依赖。CUDA 文档对不允许的操作和跨 stream 依赖作了分别说明。

这也解释了为什么“异步 API”不一定就能 capture：如果 host 后续逻辑必须读取拷贝结果才能确定 launch，仍然没有消除数据依赖。是否兼容，需要检查完整调用路径。

CUDA Graph 与 stream

stream 用来组织异步提交的 GPU 工作。在通常的执行语义下，同一 stream 中的操作按提交顺序执行；不同 stream 之间需要通过 event 等机制建立依赖。CUDA Graph 则将这些操作及其依赖保存下来，供后续重复执行。

stream 在 capture 和 replay 中承担不同的作用：

阶段 stream 的作用
capture 将 stream 内的先后顺序、stream 之间的等待关系转化为图中的依赖
replay 确定整张 graph 与图外其他工作的执行顺序

capture 期间的底层显存分配

private pool 并不意味着所有内存都必须在 capture 前精确分配完毕。需要区分 PyTorch 的 tensor 分配、底层 cudaMalloc，以及 CUDA Graph 自身的内存节点。

对于 native allocator，已有可复用 block 时，tensor 分配主要是 host 端的缓存管理。如果确实需要新的底层分配，当前源码中的 cudaMallocMaybeCapturing 会在 capture 状态下临时使用 cudaStreamCaptureModeRelaxed，再进行分配。

这种分配在 capture 阶段取得真实地址，随后由 private pool 保留，并不会在每次 replay 时重新申请一份显存。对应实现同样位于 CUDACachingAllocator.cpp。

这与 cudaMallocAsync 被捕获为 graph 的 allocation node 是不同的机制，后者由 CUDA 提供图内分配与释放语义，参见 Graph Memory Nodes。不能将 native caching allocator 的工作方式直接套用到所有 allocator backend。

这里的 relaxed mode 也不表示 kernel 会在 capture 时执行，更不会让依赖 GPU 结果的 host 同步变得有效。它只是允许框架在自行保证地址生命周期的前提下完成这类分配。

无法查询 event 时如何回收

剩下的问题是，allocator 在 eager 下可能需要查询 event，capture 时却不能照常依赖这些执行状态。

PyTorch 对此有专门的 capture 路径。native allocator 在 capture 期间跳过常规的 process_events，对需要跨 stream 跟踪的部分回收操作作延后处理。同一 stream 中可以根据依赖顺序证明安全的复用，仍然能够进行。

较新的实现还提供 graph_capture_record_stream_reuse 选项，尝试利用图的拓扑关系判断部分跨 stream 内存何时可以安全复用。这里使用的是图中已经建立的依赖，而不是查询尚未执行的 kernel 是否完成。对应逻辑可以从 allocator 源码中的 process_events、deferred_blocks 和该配置项继续阅读。

因此，capture 中的内存管理并不是暂停所有分配和释放，而是将“可以根据依赖关系确定的复用”与“需要运行时完成状态才能确定的回收”分别处理。
